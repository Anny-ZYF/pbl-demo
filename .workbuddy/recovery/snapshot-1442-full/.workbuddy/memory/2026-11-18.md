## 修复教师端附件下载失败与文件名"乱码"

问题定位（两个独立根因）：
1. `TeacherAssignmentGradingView.vue` 用裸 `<a href="/api/v1/files?key=...">` 打开附件；`/api/v1/files` 在 `SecurityConfig` 落到 `anyRequest().authenticated()`，浏览器跳转不带 JWT → 401。学生端一直用 Axios blob 下载，所以只有教师端坏。
2. `TeachingService.submit()` 把 storage key 的 UUID 文件名当作 `submission_attachment.original_name` 写库，`file_size` 写死 0。上传接口 `POST /files` 返回的真实 `originalName`/`size` 在提交时只取了 `storageKey`，元数据全丢，教师看到的是一串 UUID（被当成乱码）。

改动：
- 后端新增 `common/AttachmentNames.java`（文件名清洗 + UTF-8 mojibake 修复）、`teaching/SubmissionAttachmentInput.java`（自定义 Jackson 反序列化，兼容旧客户端字符串数组）。`StudentSubmissionRequest.attachments` 改为携带 `storageKey/originalName/fileSize`；`TeachingService.submit()` 清洗后写入真实名与大小；`TeachingMapper.insertAttachment` 改 `ON DUPLICATE KEY UPDATE` 支持同 key 刷新元数据。
- `FileController.upload` 新增可选 `name` 字段（前端 `encodeURIComponent` 的 ASCII 名），`StorageService.store` 增加三参重载；`application.yml` 配置 `server.servlet.encoding` 强制 UTF-8。`FileController.download` 改为按 `submission_attachment.original_name` 设置 `Content-Disposition`。
- 后端白名单顺手补 `rar`（前端 UI 一直承诺支持 RAR，此前上传必被后端拒绝）。
- 前端新增 `api/files.js`（通用带 JWT 上传/下载，60s 超时）、`utils/attachmentName.js`（历史 UUID 名展示兜底为「附件 N.ext」）；`student.js` 保留兼容 re-export；`http.js` 拦截器在 blob 下载失败时解析 JSON 错误体；`downloadAuthenticatedFile` 延迟 1s 释放 objectUrl。
- 三个 Vue 页面：教师批改页改认证下载按钮（含大小、加载态、错误呈现）；学生提交面板上传时收集真实名/大小；学生详情页与提交面板对历史 UUID 名做兜底展示。
- 文档同步 `docs/API_CONTRACT.md`（第 3 节明确 GET /files 必须带 Bearer、禁止裸链接；6.1 附件结构；rar）与 `docs/openapi.json`（StudentSubmissionRequest 补 attachments/contributionScores、新增 SubmissionAttachmentInput、POST /files 加 name、GET /files 加说明）。

验证：`mvn test` 85 通过 / 5 skipped（MySQL 集成），新增 12 个后端用例；`npm test` 23 通过（新增 6 个）；`npm run build` 成功；`docs/openapi.json` 合法。未做浏览器实机验证与 MySQL 迁移演练（本次未改表结构）。

注意：历史附件记录的 `original_name` 已是 UUID，无法凭空还原真实文件名，前端统一兜底展示；新提交的附件才会显示真实中文名。

历史文件名不可恢复的证据（用户追问时核查）：真实名只存在于 `POST /files` 的一次性 HTTP 响应 `StoredObject` 里；HEAD 版 `StudentSubmissionPanel.vue:31` 只取 `.storageKey`，`StudentSubmissionRequest.attachments` 是 `List<String>`，`TeachingService.submit():308` 从 key 截 UUID 段填 `original_name`、`file_size=0`。磁盘 14 个文件全为 `UUID.docx` 且无 sidecar；`submission.file_path`/`artifact_json` 无副本（后端根本不读 artifact_json）；`audit_event` 的 SUBMISSION_SAVED 只记 groupId；V2:1384 的 `originalName` 是小组重名归档，与附件无关；docx core.xml 只有作者名。V2/旧库迁移脚本也没有附件原始名。

## 确保"之后新上传的附件能看到真实名"（端到端补漏）

用户明确不再追究历史文件，只要求新上传的能看到。核查后又补了三处残留缺口：
1. `StorageAccessMapper.originalNameByKey` 原为 `ORDER BY id LIMIT 1`，同一 storage_key 被多次提交引用时会取到最旧（可能是 UUID 名）→ 改 `ORDER BY id DESC LIMIT 1`，新增 `StorageAccessMapperTest` 反射断言 SQL。
2. 前端 blob 下载忽略后端 `Content-Disposition`，落盘名只取前端展示名 → `http.js` 拦截器对 `responseType:'blob'` 返回 `{blob, headers}`；`api/files.js` 解析头得到 `filename`；新增 `attachmentName.filenameFromContentDisposition`（优先 RFC 5987 `filename*`，过滤 Spring 的 `??.docx` ASCII 近似）；`downloadFile.js` 优先用服务端名，历史 UUID 仍走「附件 N.ext」兜底。`student.js` 的 `downloadStudentFile` 兼容包装成只返回 blob，保持旧语义。
3. `TeacherAssignmentGradingView.vue` 提交列表/批改头一直显示 `fileName || '暂无文件名称'`，但 `submissions` SQL 根本不返回该字段 → 抽 `parseAttachments()` + `submissionFileLabel()`，从 `attachments`（数组或 JSON 字符串）取真实名，多个显示「X 等 N 个附件」，无附件显示「仅在线正文，无附件」。

验证：`mvn test` 87 通过 / 5 skipped，`npm test` 27 通过（新增 4 个文件名解析用例 + 后端 2 个），`npm run build` 成功。仍未做浏览器实机验证。
