# 教师端与学生端开发交接

本文档面向继续开发教师端、学生端的团队成员及其 AI 助手。当前管理员端是视觉和工程基线；教师端、学生端只有路由、统一布局和占位页，业务页面仍属于团队后续。

开始前依次阅读：

1. 根目录 `AGENTS.md`
2. [SYSTEM_DESIGN.md](./SYSTEM_DESIGN.md)
3. [API_CONTRACT.md](./API_CONTRACT.md)
4. [SCORING_ALGORITHM.md](./SCORING_ALGORITHM.md)
5. [DEPLOYMENT.md](./DEPLOYMENT.md)

## 1. 不可破坏的基线

- API 前缀固定为 `/api/v1`，统一响应由 `frontend/src/api/response.js` 解包。
- JWT 由 `frontend/src/stores/auth.js` 和 `frontend/src/utils/session.js` 统一管理，不按角色再造三套 Token。
- 前端角色统一为 `ROLE_ADMIN`、`ROLE_TEACHER`、`ROLE_STUDENT`；后端响应可为不带前缀的角色，使用现有工具标准化。
- 401 必须清理会话并回登录页；403 要显示无权限，不得伪装成空数据。
- `mustChangePassword=true` 时必须进入 `/change-password`；除读取本人、改密和退出外，后端也会拒绝其他业务接口。改密成功后清会话并用新密码重登，不得在前端绕过。
- 评分公式只在后端和算法服务实现。前端只能展示后端返回的贡献度、规则分、模型分、最终分和解释。
- 任何人工改分、发布或申诉处理都必须走现有 API，不能直接写数据库。
- 教师只能访问自己课程和作业的数据；学生只能访问自己的选课、团队、工作量、成绩和申诉。
- 保持当前管理员端的简约视觉：浅色背景、内容卡片、清楚的页面标题、少量主操作、表格/表单优先。不要引入另一套 UI 框架。

## 2. 推荐目录

```text
frontend/src/
├─ api/
│  ├─ auth.js               # 已有
│  ├─ http.js               # 已有，唯一 Axios 实例
│  ├─ teacher.js            # 团队新增
│  ├─ student.js            # 团队新增
│  └─ files.js              # 团队新增
├─ components/
│  ├─ scoring/              # 分数拆解、异常标识、解释面板
│  ├─ workload/             # W/Q 表格、合计提示、确认状态
│  └─ ...                   # 可复用小组件
├─ layouts/
│  └─ RoleLayout.vue        # 已有，可扩展菜单但保留角色隔离
└─ views/
   ├─ teacher/
   └─ student/
```

规则：一个 API 方法只在 `api/` 定义一次；页面不直接创建 Axios 实例；可复用业务展示拆成组件，但不要为单次使用过度抽象。

## 3. 开发顺序

### 阶段 0：环境与契约冒烟

完成以下动作后再写页面：

1. 按部署文档启动 MySQL、Spring Boot、可选算法服务和 Vite。
2. 分别用管理员、教师、学生账号调用 `/auth/login` 和 `/auth/me`。
3. 确认教师访问 `/admin/dashboard` 为 403，学生访问 `/teacher/courses` 为 403。
4. 用 Swagger 或 HTTP 客户端读取将要开发的接口，记录真实响应字段。
5. 如页面所需字段不在接口中，先提交后端接口变更，不要先造假字段。

### 阶段 1：共享外壳

- 为 `RoleLayout.vue` 增加教师、学生各自的最小菜单。
- 保留账号菜单、修改密码、退出和移动端折叠。
- 每个角色仅注册自己的路由；路由 `meta.roles` 必须正确。
- 建立统一的加载、错误、空状态和分页用法。
- 不新增全局状态，除非两个以上无父子关系页面需要共享且刷新策略已明确。

验收：直接输入其他角色 URL 会被路由守卫重定向；后端仍会拒绝越权请求。

### 阶段 2：教师端基础教学

按以下顺序实现：

1. **我的课程**：调用 `GET /teacher/courses`。
2. **课程作业**：调用列表、创建、发布接口；创建表单必须校验截止时间、`p=1..4`、总分和分支权重。
3. **团队管理**：调用 `GET /teacher/courses/{courseId}/students?assignmentId=...` 获取候选人，调用 `GET /teacher/assignments/{assignmentId}/groups/{groupId}/members` 获取成员；建组人数不得超过 `p+1`。
4. **提交与团队评分**：提交列表已返回 `content/filePath/note`；附件通过受鉴权 `GET /files?key=...` 下载，再录入 `groupScore` 和评语。

阶段验收：教师 A 不能读取教师 B 的课程、作业、团队或提交；权重和不为 1 的作业不能创建；非草稿作业不能重复发布。

### 阶段 3：学生端基础教学

按以下顺序实现：

1. **我的课程与作业**：只展示有效选课及已发布/结束态作业。
2. **我的团队**：补齐团队成员详情接口后展示成员和组长。
3. **团队作品提交**：正文或附件至少有一项；附件先调用文件上传，再把 `storageKey` 作为 `filePath` 提交。

阶段验收：非团队成员不能提交；截止后返回冲突时显示明确原因；重复提交更新同一团队作业的最新提交，不在前端制造重复记录。

### 阶段 4：工作量确认

教师端：

- 用“成员 × 评价分支”矩阵展示份额。
- 每个分支实时计算合计，只有误差允许范围内等于 1 才允许提交。
- 每个分支必须包含完整成员集合。
- 证据字段用于说明分配依据，不得填入无关敏感信息。

学生端：

- 完整展示各分支的全员份额和证据。
- `CONFIRMED` 与 `OBJECTED` 必须是明确动作；异议时原因必填。
- 提交后刷新服务器状态，不在本地假设工作量已锁定。

阶段验收：有任一成员 `OBJECTED` 时不能发起评分；全部确认后工作量变为 `LOCKED`；教师修订应创建新版本，不覆盖已锁定快照。

### 阶段 5：评分复核与发布

教师端评分页最少展示：

- 学生、贡献度 `contribution`
- 团队作品分 `groupScore`
- 规则分 `ruleScore`
- 模型分 `modelScore`（可能为空）
- 模型—规则偏差 `modelRuleDelta`
- 异常标记 `anomaly`
- 建议/当前最终分 `finalScore`
- `explanation` 中的规则版本、分支、基准分、阈值、有效贡献度、模式和模型说明

交互规则：

- `mode=model`、`rule_fallback`、`rule_only` 要用中性、可理解的文案，不把回退渲染为系统崩溃。
- `anomaly=true` 要突出，但不能自动否决结果。
- 本次运行每名成员都必须提交复核决定。
- 最终分与当前建议分不同超过后端容差时，调整原因必填。
- 只有运行变为 `APPROVED` 后才显示发布动作。
- 发布需二次确认，说明发布后学生可见并开始 7 天申诉期。

阶段验收：未复核全员不能批准；批准前不能发布；学生在发布前看不到结果；发布后显示的最终分与教师复核一致。

### 阶段 6：成绩解释与申诉

学生成绩页：

- 默认突出教师最终分，同时把团队分、贡献度、规则分、模型分分区展示。
- 模型分为空时显示“本次采用规则评分”，不能显示 0。
- 解释面板只翻译后端字段，不在浏览器复算公式。
- 申诉按钮根据 `publishedAt + 7 天` 显示可用状态；最终是否超期仍以后端响应为准。

教师申诉页：

- 展示学生、作业、理由、证据、提交时间和当前状态。
- 只允许 `ACCEPTED` 或 `REJECTED`。
- 接受时调整后分数必填且为 `0..100`；两种结论都必须填写处理说明。
- 处理后重新读取列表，不能只改本地状态。

阶段验收：同一成绩不能有两个未处理申诉；超期申诉返回 409；教师不能处理他人作业申诉；接受申诉后学生成绩反映调整值。

## 4. 可选后端增强项

教师课程学生候选名单、教师/学生团队成员详情、提交正文/附件字段、教师工作量详情、学生申诉列表和受鉴权文件下载均已实现，不得再用假数据代替。首版页面需要的后端闭环已经齐备，可选增强项为：

1. 教师/学生专用工作台聚合接口；当前可组合已有列表。
2. 文件内联预览、删除与保留期限治理；受鉴权下载已经可用。
3. 通知、导出、作业归档和更丰富的工作量版本时间线。

新增读取接口也必须做资源归属校验，不能只依赖前端传入的教师 ID 或学生 ID。

## 5. 前端实现规范

### API 与状态

- 只向页面返回解包后的 `data`，不要让页面重复判断 `code`。
- 接口参数名严格使用 Java DTO 的 camelCase。
- 分页统一使用 `{items,total,page,pageSize}`。
- 日期传 ISO 本地日期时间；展示统一走格式化工具。
- 金额/分数用数值输入并限制范围；份额内部使用 `0..1`，UI 可显示百分比但提交前必须除以 100。
- 后端状态值原样保存；中文标签由集中映射函数生成，不在各页面散落判断。
- 不吞掉 409。它通常表示状态已被其他人改变，提示后应重新加载数据。

### 表单与并发

- 提交按钮在请求期间禁用，防止重复提交。
- 删除、发布、停用、复核、申诉结论等重要动作需要二次确认。
- 收到成功响应后从服务器重新读取关键实体。
- 不用数组下标当业务主键；`scoreResultId`、`workloadSetId`、`runId` 必须来自接口。

### 可访问性与简约风格

- 表单有可见标签和错误提示；不能只依赖 placeholder。
- 键盘可操作所有主要动作；弹窗关闭后焦点回到触发按钮。
- 颜色不是状态的唯一表达方式，异常、回退和通过都需文字。
- 小屏下表单改为单列，核心操作不被横向表格完全遮挡。
- 一页只保留 1 个主要操作；次要操作使用文本按钮或更多菜单。

## 6. 测试与验收清单

### 每次提交前

```powershell
# 前端
Set-Location frontend
npm test
npm run build

# Java
Set-Location ..\backend
mvn test

# Python 算法
Set-Location algorithm-service
pytest -q
```

这些是应执行的命令，不代表某个未来提交已经通过。提交说明必须写明本次实际执行了哪些命令及结果。

### 教师端验收

- [ ] 教师只看到自己的课程。
- [ ] 作业分支权重和不为 1 时无法提交。
- [ ] 标准组规模与团队人数限制和后端一致。
- [ ] 能完成建组、查看作品、录入团队分。
- [ ] 工作量矩阵包含全部分支和成员，每分支份额和为 1。
- [ ] 能区分待确认、异议、锁定状态。
- [ ] 评分页完整展示规则分、模型分、偏差、异常和解释。
- [ ] 模型不可用时仍能复核规则回退结果。
- [ ] 改分必须说明理由；全员复核后才能批准和发布。
- [ ] 只能处理本人作业的申诉。

### 学生端验收

- [ ] 学生只看到自己的有效选课和团队。
- [ ] 只能查看已发布作业并在截止前提交。
- [ ] 正文和附件至少一项非空。
- [ ] 能查看全员工作量并确认或提出带理由的异议。
- [ ] 未发布成绩不可见。
- [ ] 最终分与规则分、模型分的标签没有混淆。
- [ ] 模型分为空时不显示为 0。
- [ ] 7 天内可申诉，超期和重复未结申诉有明确提示。
- [ ] 能查看申诉处理结果（依赖待补接口）。

### 跨端闭环验收

- [ ] 管理员创建教师、学生账号，首次登录能修改密码。
- [ ] 教师创建并发布含多个评价分支的作业。
- [ ] 教师建立团队，学生提交作品。
- [ ] 教师录入团队分和工作量，所有学生确认后锁定。
- [ ] `p=4` 分别验证模型可用与模型回退；`p!=4` 验证 `rule_only`。
- [ ] 偏差严格大于 2 才标记异常，等于 2 不标记。
- [ ] 教师复核、发布，学生查看解释并申诉，教师处理。
- [ ] 管理员能在评分运行、异常和审计中追踪上述关键动作。
- [ ] 关键请求的响应头和响应体包含同一个 `requestId` 语义链路。

## 7. AI 协作要求

给 AI 的任务应包含：目标角色、页面、对应 API、允许修改的目录和验收命令。推荐模板：

```text
只实现教师端“工作量分配”页面；允许修改 frontend/src/views/teacher、
frontend/src/components/workload、frontend/src/api/teacher.js 和路由。
严格使用 docs/API_CONTRACT.md 中的接口，不修改评分公式或后端状态。
完成后运行 npm test 与 npm run build，并报告实际结果。
```

AI 不能自行决定以下事项：

- 更改公式或异常阈值；
- 放宽角色/资源归属校验；
- 直接改生产数据库；
- 使用假数据掩盖接口缺口；
- 将模型建议自动发布为最终成绩；
- 宣称未运行的测试已通过。

## 8. 完成定义

一个页面只有同时满足以下条件才算完成：

1. 使用真实接口并覆盖成功、空数据、校验失败、401、403、404/409 和网络失败。
2. 路由与角色守卫正确，后端资源归属验证通过。
3. 页面字段、请求体和状态与 `API_CONTRACT.md` 一致。
4. 关键动作刷新服务器状态并有审计事件。
5. 响应式和键盘操作可用。
6. 已实际运行相关测试/构建，并在交接说明中记录结果。
7. 对新增接口或状态同步更新相关文档。
